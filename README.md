# MilesAhead

A self-hosted content aggregation platform that scans miles and points websites, generates articles using AI, and publishes them after admin review. Includes 52 curated credit card reference pages with the Scout persona.

**Live:** [milesahead.kumaranik.com](https://milesahead.kumaranik.com)

## Features

- **Automated Scanning** — RSS scraping of 6+ miles/points sources every 2-4 hours
- **AI Pipeline** — Dual-model: Nemotron generates articles, Llama 70B verifies accuracy
- **Duplicate Stories** — Each scan clusters the last 48h of scanned posts by title and generates one article per multi-source cluster, after two checks. The raw-ID check skips a cluster that reuses a source some article was written from, and records the cluster's other posts in `covered_raws` so that late coverage cannot come back as a second article once the original sources age out. The story check (`internal/storydedup`, `scanner.story_dedup`) compares the cluster with every article from the last 7 days: a TF-IDF prefilter, then one short AI call on the enrichment chain ("same story? materially new?"). It runs in `shadow` mode, logging `story dedup decision` and counting `milesahead_story_dedup_decisions_total` without blocking, until its decisions have been reviewed
- **Image Pipeline** — 4-source search (Unsplash, Pexels, Openverse, Wikimedia) with vision model scoring
- **Reference Pages** — 52 credit card guides across 6 categories with Scout persona verdicts
- **Card Comparison** — Side-by-side comparison of 2-3 cards (earning rates, credits, benefits, protections, transfer partners)
- **Card Infographics** — Designed infographics on card pages: a teaser in the card-art slot opens the full image in an in-page viewer
- **Article Tags** — AI-generated tags from 8 categories; six of them are topic filters on the homepage, combinable with the article type
- **Admin Dashboard** — Review queue with approve/reject/revise workflow, newsletter admin workflow
- **Magazine-Style Site** — Dark/light mode, two-column articles, type and topic filters, RSS feed
- **Branding** — The mountain mark, misty header, home hero and footer band from the card infographics, as SVG in `static/img/brand/` (ridges generated by `scripts/brand/gen_band.py`); PNG copies for email, the favicon and the default share image come from `scripts/brand-images.sh`
- **Newsletter** — Weekly newspaper-style email with Scout's Pick, Card of the Week, tag-grouped articles
- **Ended Offers** — An article's offer end date comes from its Key Details (`internal/offer`, stored in `expires_on`, recomputed on startup). Only a short fixed list of labels counts ("Deadline", "Booking Deadline", "Registration Deadline", "Promotion Period", "Booking Window", "Expiration Date", ...; see `endLabels`), and the offer ends on the latest date any of them names. A value that says the offer is ongoing, open-ended, unannounced or extended without a new date, or a separate "Extended/New Deadline" detail, leaves the article with no end date. The rule is built to err late: its known early case is a year-less date such as "December 31" written in the first two weeks of January, read as the one just gone. Once that day is over in Hawaii (the westernmost US time zone, so an "11:59 PM PT" deadline is never called early), the offer leaves the default home feed and the newsletter, is badged "Ended" ("Deadline passed" for a news story) in filtered views, search, card pages and the RSS feed, and its page shows an "offer ended" note
- **Zero Cost** — OCI free-tier compute, NVIDIA API, SQLite

## Tech Stack

- **Language:** Go 1.26+
- **Database:** SQLite (WAL mode)
- **AI:** NVIDIA API (Nemotron, Llama 70B, Llama Vision)
- **Deployment:** OCI ARM VM, Caddy, systemd, GitHub Actions CI/CD
- **Observability:** Grafana Cloud (Prometheus + Loki via Alloy)

## Quick Start

```bash
git clone https://github.com/anik-apps/milesahead.git
cd milesahead
cp config.example.yaml config.yaml
# Edit config.yaml with your NVIDIA API key and admin password
go build -o milesahead ./cmd/milesahead
./milesahead
```

Seed credit card reference pages and structured comparison data:
```bash
go run ./cmd/seed-cards
go run ./cmd/seed-structured
```

### Choosing AI models

Providers retire models without warning, and the catalogue endpoint is not a
liveness signal — of 81 models it advertised, only 9 answered. Verify any change
to `generator_model`, `fallback_generator_model` or `critic_model` by measuring
it against real source material rather than trusting the listing:

```bash
# Which models answer at all, and do they honour the critic's JSON contract?
go run ./cmd/ab-models -critic-candidates "model-a,model-b" -generators model-a

# Score candidate generators on real clusters, using one fixed critic
# (-critic-no-thinking sends the critic requests the way production does)
go run ./cmd/ab-models -topics 5 -generators "model-a,model-b" -critic model-c

# Dump whole articles for human review, then render them side by side
go run ./cmd/ab-models -full -generators model-a -critic model-c -out a.json
python3 scripts/render_article_review.py a.json b.json > compare.html
```

The app also runs a startup preflight against every configured model and logs
`ERROR` if nothing can generate or no critic answers, so a retired model surfaces
at boot rather than as articles quietly never appearing. Results are exported as
`milesahead_ai_preflight_models_reachable{role}`; `role="critic"` at 0 means
nothing can publish. Article-path models are probed under the full
`request_timeout`, so with a slow critic the result arrives minutes after boot.

`critic_model` is a chain (`nvidia/nemotron-3-super-120b-a12b`, then
`moonshotai/kimi-k3`), tried in order when a critic is overloaded or gone; one
reachable critic is enough to publish. `critic_disable_thinking: true` sends
`chat_template_kwargs: {enable_thinking: false}` on critic requests only — with
thinking on, nemotron-super truncates or leaks its reasoning into the JSON. The
`critic scored` log line names the model that scored.

### Enrichment

Scout's Take, key details, tags and the article image are **not** produced during
article generation. They run as a background reconciliation pass
(`internal/enrich`) on `enrichment_interval`, against `enrichment_model` — a
separate chain from the critic, so a degraded critic backend cannot take them
down with it. The same chain serves every other short AI call: image
text-scoring, the newsletter pick, card-update detection and the pipeline's
inline key-details call. Those are capped at 30 seconds, so the critic is used
for verification only.

This matters because inline they were best-effort: a single slow response
permanently cost the article a field, and for two and a half months roughly a
quarter of articles published with one missing. Reconciled, a miss is simply
picked up next pass. `enrichment_max_attempts` bounds how long an article keeps
being retried, and `milesahead_articles_degraded` reports how many are still
missing something.

### Revisions

Feedback from the dashboard or an email reply puts an article in
`revision_requested` and starts the AI rewrite straight away. A revision
reconciler (`article.Manager.ProcessPendingRevisions`) also sweeps every 5
minutes and shortly after startup, so a rewrite that failed or was cut off by a
deploy is retried rather than left "Revising" forever. Retries back off and stop
after 5 failures, at which point the dashboard shows "Revision failed N times"
and `milesahead_revisions_waiting{state="exhausted"}` counts it.

### Editor notes

A remark for the admin rather than readers ("Could not find a link for: ...")
is an editor note. If generated text contains one (`<div class="editor-note">`)
it is split out before the article is stored, kept in the admin-only
`editor_notes` column and shown in the dashboard preview and the review email.
Content is never stored with notes, and anything that loads an article (pages,
feed, newsletter, excerpts, search index, prompts) strips any still inline in
older rows (`internal/editornote`). To move notes out of articles stored before
this, run the one-off tool (a read-only dry run unless `-apply` is given; it
takes no backup, so take one first):

```bash
go run ./cmd/repair-editor-notes -db ./data/milesahead.db          # dry run
go run ./cmd/repair-editor-notes -db ./data/milesahead.db -apply   # write
```
